## F1. 평가 입력과 결과 키의 일치 보장

**문제와 영향:** 결과 키에 들어간 해시의 데이터와 실제 평가한 데이터가 달라질 수 있다. 그 결과가 정상 완료된 결과로 저장되면 캐시 재사용과 커밋별 비교의 근거가 오염된다.

- 발생 조건: 해시 계산·검증 이후부터 평가 결과 저장 전까지 데이터셋이나 평가 코드가 변경된다. 여러 샤드가 서로 다른 시점의 파일을 읽을 수도 있다.
- 확인한 재현: 데이터 `XYZ`의 해시를 계산한 뒤 평가 직전에 `ABC`로 바꿨다. 가짜 탐지기가 `ABC`를 탐지한 결과가 `XYZ`의 해시로 저장됐다.
- 코드 확인: 실행 중인 서비스의 코드 변경 검사는 사이클 시작에만 있다. 코드 변경 도중 샤드 실행의 일관성도 보호해야 한다.
- 관련 코드: [service.py](pipeline/service.py)의 `cycle()`, [runner.py](pipeline/runner.py)의 `discover()`, `benchmark()`, `evaluate()`, [shard.py](pipeline/shard.py)의 `load_range()`.

수정 방향: 평가에 사용할 데이터와 코드를 고정해 그 사본으로 해시 계산과 평가를 수행하거나, 실행 중 변경을 감지한 작업의 결과를 폐기한다. 현재 파일의 해시만 새로 붙여 이미 계산한 결과를 저장하는 것으로는 해결되지 않는다.

완료 기준:

- [ ] 정상 실행에서 결과 키·메타데이터·평가 입력의 버전이 일치한다.
- [ ] 평가 도중 데이터 변경 시 고정된 원본으로 일관되게 평가하거나, 해당 작업을 중단하고 결과를 게시하지 않는다.
- [ ] 평가 코드 변경도 동일하게 처리하며, 옛 코드와 새 코드를 섞은 결과를 저장하지 않는다.
- [ ] 변경 감지로 폐기된 작업은 현재 입력으로 다시 평가할 수 있다.

## F2. metric-task 결과 귀속과 미측정 처리

**문제와 영향:** 어떤 코드로 실행했는지 확인할 수 없는 배치를 특정 커밋의 결과로 표시하거나, 측정하지 않은 실행을 ‘서버 누출 없음’으로 계산한다. 작업 성공률과 누출률을 신뢰할 수 없게 만드는 문제다.

### F2-a. dirty·resume 실행의 커밋 귀속

- 발생 조건: 커밋하지 않은 수정이 있는 PromptGuard 체크아웃으로 실행하거나, 다른 커밋으로 이동한 뒤 같은 배치를 `--resume`한다.
- 현재 동작: `m2.py`는 HEAD만 기록한다. resume에서는 기존 성공 실행을 유지하면서 `batch.json`을 현재 커밋·설정으로 덮어쓴다. 대시보드는 이 메타데이터를 그대로 믿고 커밋에 붙인다.
- 근거 수준: 코드 경로 확인. dirty 정보가 없는 기존 배치가 실제로 clean 상태였는지는 이 파일들만으로 확인할 수 없다.
- 관련 코드: [m2.py](../metric-task/scripts/m2.py)의 `cmd_run()`, [task.py](pipeline/task.py)의 `summarize()`, [service.py](pipeline/service.py)의 `write_index()`.

수정 방향: 상위 평가기에서 실행 출처를 기록하고 resume의 기존 출처·설정을 검증한다. 대시보드는 clean, dirty, 이력 미확인을 구분한다. 대시보드 표시만 바꿔서는 기록하지 않은 출처를 복원할 수 없다.

완료 기준:

- [ ] dirty 실행은 clean 커밋의 대표 결과와 구분된다.
- [ ] 다른 커밋·평가 설정으로 resume하면 실행을 거부하거나 별도 배치로 분리한다.
- [ ] 기존 실행의 출처를 새 `batch.json`으로 덮어쓰지 않는다.
- [ ] 출처 정보가 없는 기존 배치는 ‘이력 미확인’으로 표시한다.

### F2-b. 미측정 서버 누출을 0으로 처리

- 발생 조건: 요청 기록을 켠 실행과 끈 실행이 같은 배치에 섞이거나, 유효한 실행 행의 `server_leaked`가 비어 있다.
- 현재 동작: 배치의 `capture` 값과 CSV 열 존재 여부만 확인하고, 빈 값을 0으로 바꿔 전체 유효 실행 수로 나눈다.
- 확인한 재현: 누출이 발생한 측정 실행 1개와 미측정 실행 1개를 넣으면 누출률이 50%로 나온다. 측정한 실행만 기준으로 하면 1/1이며, 나머지 1개는 미측정이다.
- 관련 코드: [task.py](pipeline/task.py)의 `summarize()`, `_int()`, [app.js](web/app.js)의 `renderTask()`.

완료 기준:

- [ ] 각 실행의 측정 여부를 구분하고, 누출률 분모에는 측정한 실행만 포함한다.
- [ ] 측정한 실행 수와 미측정 실행 수를 화면에서 확인할 수 있다.
- [ ] 모두 미측정이면 누출률은 0%가 아닌 미측정 상태다.
- [ ] 과제 성공률 등 다른 지표의 분모는 각 지표의 정의를 따른다.

## F3. 설정한 저장소와 실제 평가 대상의 일치

**문제와 영향:** 화면에 표시한 저장소와 실제로 평가한 저장소가 다를 수 있다. 다른 프로젝트의 결과를 현재 프로젝트의 결과처럼 보여준다.

- 발생 조건: 기존 데이터 폴더를 유지하면서 `--repo`를 A에서 B로 변경한다.
- 현재 동작: bare 저장소가 이미 있으면 요청한 URL을 확인하지 않고 기존 `origin`에서 fetch한다. index의 저장소 표시는 새 설정 B를 사용한다.
- 확인한 재현: 서로 다른 로컬 저장소 A·B로 연속 실행해도 실제 커밋 목록은 A에 남았다.
- 관련 코드: [repo.py](pipeline/repo.py)의 `sync()`, [service.py](pipeline/service.py)의 `plan()`, `write_index()`.

완료 기준:

- [ ] 기존 `origin`과 요청한 평가 대상이 일치하는지 검증한다.
- [ ] 다른 대상이면 명확한 오류로 중단하거나 B로 전환하고 B의 커밋을 수집한다.
- [ ] B를 표시하면서 A의 커밋·평가 결과를 게시하는 상태가 발생하지 않는다.

## F4. 일시적인 결과 요청 실패 후 화면 복구

**문제와 영향:** 일시적인 네트워크 오류가 ‘예시 없음’으로 굳거나 결과 패널을 비운다. 실패한 요청과 실제로 데이터가 없는 상태를 구별할 수 없다.

- 발생 조건: examples, summary, latency 또는 task JSON 요청이 한 번 실패한 뒤 네트워크가 복구된다.
- 현재 동작: `loadExamples()`는 실패를 `[]`로 바꾼 Promise를 계속 캐시한다. 다른 결과 요청은 `null`이 되지만, index가 그대로인 동안 일반 상태 폴링으로 다시 읽지 않는다.
- 확인한 재현: 예시 요청에 503을 한 번 반환하면 다시 열어도 두 번째 HTTP 요청이 없다. summary 요청 실패 후에는 정상 상태 응답을 두 번 받아도 summary를 재요청하지 않았다.
- 관련 코드: [app.js](web/app.js)의 `loadExamples()`, `loadResults()`, `fetchTask()`, `pollStatus()`.

기존 [BUGS.md](BUGS.md)의 요청 실패 수정은 index·상태 요청에 관한 것이다. 이 항목은 결과 파일과 예시 요청에 남아 있는 복구 문제다.

완료 기준:

- [ ] 요청 실패와 실제 빈 데이터를 별도 상태로 표시한다.
- [ ] 실패한 예시 캐시는 다시 요청할 수 있다.
- [ ] 서버 모드에서는 index가 바뀌지 않아도 실패한 결과 요청을 재시도한다.
- [ ] 정적 사본에서도 실패한 요청을 사용자가 다시 시도할 수 있다.
- [ ] 커밋 전환과 재시도가 겹쳐도 현재 선택한 커밋·결과 키에 해당하는 응답만 표시한다.

## F5. 예시의 Unicode 위치 오류

**문제와 영향:** 원문의 강조 범위와 ‘모델에 간 텍스트’가 실제 평가 출력과 다르다. 탐지기가 제대로 가렸는데도 일부 비밀이 남았다고 오해할 수 있다.

- 발생 조건: 예시 창 안에서 정답·가림 범위 앞이나 안에 이모지 등 UTF-16 두 칸을 사용하는 문자가 있다.
- 현재 동작: 서버의 Python 문자 위치를 JavaScript의 `slice()` 위치로 그대로 사용한다.
- 확인한 재현: `🔑 secret=ABC`에서 Python 기준 `[9, 12)`를 전달하면 `ABC` 대신 `=AB`를 강조한다. 마스킹 화면은 정답인 `🔑 secret=[SECRET_1]` 대신 `🔑 secret[SECRET_1]C`가 된다. 저장된 결과에서도 영향을 받는 예시를 확인했다.
- 관련 코드: [collect.py](pipeline/collect.py)의 `_example()`, [app.js](web/app.js)의 `highlighted()`, `maskedText()`, `exampleDetail()`.

완료 기준:

- [ ] 서버와 화면 사이의 위치 단위를 명확히 정하고 필요한 변환을 적용한다.
- [ ] 보조 평면 문자가 범위 앞·안·뒤에 있는 경우 모두 강조와 마스킹 결과가 정확하다.
- [ ] 여러 범위와 잘린 예시 창에서도 위치가 일치한다.
- [ ] 서버의 예시 형식을 바꾼다면 결과 버전·키를 갱신해 이전 형식과 구분한다.

## G1. Guard 사용 전 필수: 실패한 요청을 0ms로 집계

**문제와 영향:** 탐지 호출이 실패해 시간을 알 수 없는 요청을 빠른 정상 요청처럼 표시한다.

- 발생 조건: `--latency-guard`로 재생한 요청의 호출에 성공한 시간 표본이 없다.
- 현재 동작: `condense()`가 누락된 중앙값을 `or 0`으로 바꿔 합산한다.
- 확인한 재현: 호출 1개가 실패한 Guard 요청 1개의 p50·p95·max가 모두 0ms가 됐다.
- 관련 코드: [latency.py](pipeline/latency.py)의 `condense()`, `headline()`, [app.js](web/app.js)의 `renderLatency()`.

완료 기준:

- [ ] 시간을 계산할 수 없는 요청은 실패·미측정으로 구분하고 정상 지연 통계에 0ms로 섞지 않는다.
- [ ] 화면에서 정상 측정 수와 실패·미측정 수를 확인할 수 있다.
- [ ] 캐시 통과로 실제 검사 호출이 0개인 정상 요청과, 호출 실패로 표본이 없는 요청을 구별한다.
- [ ] 결과 형식·집계를 바꾸면 `LATENCY_VERSION`을 올려 다시 측정한다.

## G2. Guard 사용 전 필수: 여러 배치의 세션 충돌

**문제와 영향:** 별개 실행의 표본을 합쳐 세션 수와 요청 지연을 잘못 계산한다.

- 발생 조건: 여러 배치 폴더를 `--latency-guard`로 함께 읽고, 두 배치에 같은 과제·조건·반복 이름이 있다.
- 현재 동작: 세션 이름이 `<task>/<condition>-r<n>`이므로 배치를 구분하지 못한다. 집계는 같은 세션·요청·호출 번호의 표본을 한데 모은다.
- 확인한 재현: 두 배치의 `t01/none-r1` 요청이 각각 10ms·100ms일 때 세션 수는 2개 대신 1개, 요청 p95는 100ms 대신 10ms로 나왔다.
- 관련 코드: [m4_workloads.py](../metric-latency/scripts/m4_workloads.py)의 `_session_name()`, `guard_sessions()`, [latency.py](pipeline/latency.py)의 `condense()`.

완료 기준:

- [ ] 각 capture의 출처를 구별하는 세션 식별자를 사용한다.
- [ ] 배치가 다르면 과제·조건·반복·요청 번호가 같아도 표본이 섞이지 않는다.
- [ ] 10ms·100ms 두 요청의 재현에서 세션 수 2개와 p95 100ms가 나온다.
- [ ] 식별 방식 변경으로 지연 결과 키가 갱신되며, 이전 집계 결과를 그대로 재사용하지 않는다.

## 검증과 수정 범위

기존 대시보드 테스트 44개와 JavaScript 문법 검사는 리뷰 당시 통과했다. 위 재현 검사는 임시 테스트와 코드 검토로 수행했으며, 해당 회귀 테스트는 아직 저장소의 테스트 모음에 추가되지 않았다. 화면 로직은 Node의 DOM 대역으로 확인했고, 실제 브라우저 클릭·배치 검증은 수행하지 못했다.

수정할 때는 각 완료 기준을 회귀 테스트로 추가한다. metric-task의 출처·resume 검증은 가짜 실행과 fixture로 확인할 수 있으므로 유료 Claude 실행은 필요하지 않다. 공식 P/R/F1 채점 정의는 유지하며, 결과 키나 형식이 달라지는 수정은 이전 캐시와의 구분 및 재평가까지 포함해 완료한다.
