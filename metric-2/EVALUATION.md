# 지표 2 평가 해석: 작업 성공률과 비밀 노출률

지표 2는 비밀을 마스킹했을 때 코딩 에이전트의 작업 수행이 어떻게 달라지는지 평가한다. 작업 성공률은 비밀 노출률과 함께 읽어야 한다. 성공률이 높거나 gold와 같다는 사실만으로 비밀 보호 성능이 좋다고 판단할 수는 없다.

이 문서는 [실험 구성과 측정 정의](README.md), [결과 요약](results/summary.md), [실행별 데이터](results/runs.csv)를 바탕으로 평가 조건의 역할과 결과를 해석하는 기준을 정리한다.

## 1. none, gold, promptguard의 역할

| 조건 | 의미 | 평가에서의 역할 |
|---|---|---|
| `none` | 비밀을 마스킹하지 않음 | 마스킹이 없을 때의 작업 성공률 기준선 |
| `gold` | 과제에 심은 정답 비밀만 정확히 마스킹 | 정확한 마스킹을 적용했을 때의 작업 성공률 기준선 |
| `promptguard` | 실제 PromptGuard 탐지 결과를 마스킹 | 탐지 누락, 과잉 마스킹, placeholder 차이 등을 포함한 실제 시스템의 결과 |

세 조건은 같은 Mod와 MCP bridge를 사용하며 탐지기를 바꾼다. gold는 이상적인 비밀 탐지 조건이지, 작업 성공률의 상한이나 완벽한 작업 수행 에이전트가 아니다. none 역시 작업 수행 기준선이며 성공률 100%를 보장하지 않는다.

- **none과 gold 비교:** 정확한 마스킹을 적용한 조건에서 작업 성공률이 얼마나 달라지는지 본다.
- **gold와 promptguard 비교:** 실제 탐지 및 마스킹 결과가 gold와 다를 때 작업 수행에 어떤 차이가 생기는지 본다.

성공률 차이의 원인을 판단하려면 과제별 결과와 실행 기록도 확인해야 한다. 관측된 차이에는 모델의 전략 선택과 실행 변동도 포함되므로, 모든 차이를 탐지 오류의 영향으로 단정할 수는 없다.

## 2. 비밀값이 필요한 것과 모델이 원문을 보는 것은 다르다

`needs_secret_value=true`는 과제 수행 과정에 실제 비밀값이 필요하다는 뜻이다. 모델이 그 원문을 직접 알아야 한다는 뜻은 아니다.

모델은 비밀이 저장된 파일이나 환경변수를 참조하는 명령을 만들고, 로컬 도구가 실제 값을 처리하도록 할 수 있다.

| 유형 | 실제 비밀값이 필요한 이유 | 모델이 원문을 보지 않고 수행하는 방법 |
|---|---|---|
| `property` | JWT 만료 시각, 키 모드, 비밀번호 정책 등 속성 확인 | 로컬 Python이나 셸에서 검사하고 필요한 결과만 출력 |
| `use` | API나 DB CLI 인증 | `.env`를 로드한 뒤 환경변수로 실제 값을 전달 |
| `transport` | 비밀값을 다른 파일로 이동 | 로컬 스크립트가 원문을 읽어 목적지에 기록 |

예를 들어 t17의 성공한 실행은 다음 방식으로 DB CLI를 호출했다.

```bash
set -a
. ./.env
set +a
python3 bin/minidb.py \
  --user "$REPORTING_DB_USER" \
  --password "$REPORTING_DB_PASSWORD" \
  count users --where active=0
```

모델은 변수 이름만 작성한다. 실제 비밀번호는 셸이 로컬 파일에서 읽어 CLI에 전달한다. 따라서 이 과제들은 비밀을 사용하는 능력을 평가하지만, 모델에게 비밀 원문을 공개해야만 풀 수 있도록 구성된 과제는 아니다.

## 3. 현재 평가는 placeholder 자동 원복 기능 없이 수행했다

현재 Mod는 도구 입력을 그대로 실행하고, 도구 실행 결과 등을 모델에 전달하기 전에 마스킹한다. 모델이 도구 입력에 쓴 placeholder를 실제 비밀값으로 복원하는 기능은 없다.

따라서 다음 입력은 실제 비밀번호로 바뀌지 않는다.

```bash
python3 bin/minidb.py --user report_reader \
  --password '[PASSWORD_2]' count users --where active=0
```

CLI에는 `[PASSWORD_2]`라는 문자열이 그대로 전달되어 인증에 실패한다. t17의 gold 3회와 promptguard 1회 실패가 이 방식이었다.

도구 실행 전에 placeholder를 원복하는 기능을 추가하면 이 실패 유형을 해결할 가능성이 있다. 다만 이는 현재 결과에 포함되지 않은 기능이며, 효과는 추가 후 재평가해야 한다. 원복이 있어도 모델에게 보이는 정보는 마스킹된 상태이므로, 비밀의 속성 확인이나 동일성 비교에는 적절한 도구 사용 또는 일관된 placeholder 체계가 필요하다.

## 4. PromptGuard가 완벽해지면 gold에 가까워지는가

PromptGuard가 gold와 동일한 범위와 방식으로 마스킹하고, 모델·과제·도구·실행 설정도 같다면 모델이 받는 입력 조건이 같아진다. 이 경우 두 조건의 기대 작업 성공률도 같아지는 것이 평가의 기본 기대다. 유한한 반복 실험에서는 관측 성공률이 다를 수 있다.

여기서 동일한 마스킹은 탐지 범위뿐 아니라 비밀 유형, placeholder 생성과 재사용 방식 등 모델에 보이는 표현까지 포함한다. 같은 비밀을 찾더라도 파일마다 서로 다른 placeholder를 붙이면 작업 수행 조건이 달라질 수 있다.

그러나 **완벽해지면 gold와 같아진다는 기대가, 탐지 성능 개선에 따라 성공률이 항상 한 방향으로 움직인다는 뜻은 아니다.**

- 탐지 누락을 고치면 모델이 보던 비밀이 가려진다. 비밀 노출률은 낮아지지만 작업 성공률도 낮아지면서 gold에 가까워질 수 있다.
- 과잉 마스킹을 고치면 작업에 필요한 비밀 아닌 정보가 다시 보인다. 작업 성공률이 높아지면서 gold에 가까워질 수 있다.

gold와 promptguard의 마스킹 범위는 일반적으로 포함 관계가 아니다. gold는 정답 비밀을 가리고, promptguard는 일부 비밀을 놓치면서 일부 비밀 아닌 값도 가릴 수 있다. 따라서 `none ≥ gold ≥ promptguard`라는 성공률 순서는 보장되지 않는다.

실행을 100만 번으로 늘려도 이 관계는 달라지지 않는다. 반복은 각 조건의 성공 확률을 더 정확히 추정하게 할 뿐, 성공 확률의 순서를 보장하지 않는다.

## 5. gold와의 차이가 줄어들면 언제 의미가 있는가

gold와의 작업 성공률 차이를 비밀 노출률과 함께 확인해야 한다. 노출률이 이미 0%라면 이를 유지하면서 과잉 마스킹을 줄여 작업 성공률을 높이는 것도 의미 있는 개선이다. 노출률이 매번 함께 감소해야만 개선인 것은 아니다.

| 변화 | 해석 |
|---|---|
| gold와의 차이 감소 + 비밀 노출률 감소 | gold에 가까운 보호와 작업 수행 조건으로 이동하는 방향. 성공률 자체가 올랐는지 내렸는지도 구분해야 함 |
| gold와의 차이 감소 + 노출률 0% 유지 + 작업 성공률 상승 | 관측된 보호 수준을 유지하면서 작업 수행 개선 |
| gold와의 차이 감소 + 비밀 노출률 증가 | 비밀을 더 보여줘서 작업이 쉬워졌을 가능성. 보호 성능 개선의 증거로 볼 수 없음 |
| gold와의 차이 감소 + 노출률이 높은 상태로 유지 | 작업 성공률만으로 gold에 가까운 보호 성능이라고 판단하기 어려움 |

gold와의 수치 차이를 줄이는 것 자체가 최종 목표는 아니다. **비밀 노출을 낮게 유지하면서 높은 작업 성공률을 얻는 것**이 목표이며, gold는 정확한 마스킹을 적용했을 때의 비교 기준이다.

또한 전체 성공률이 같아도 과제별 동작은 다를 수 있다. 탐지 누락으로 성공한 과제와 과잉 마스킹으로 실패한 과제가 상쇄될 수 있으므로, 같은 성공률을 같은 탐지 성능으로 해석하면 안 된다.

## 6. 현재 결과에 적용하면

비밀값이 필요한 과제에서 gold는 18/21, promptguard는 20/21 성공했다. 차이는 모두 t17에 집중되어 있다.

| 과제 범위 | gold | promptguard |
|---|---|---|
| t17 DB CLI 조회 | 0/3 | 2/3 |
| 나머지 비밀값 필요 과제 6개 | 18/18 | 18/18 |

gold의 t17 실행은 모두 placeholder를 비밀번호로 전달했다. promptguard의 성공한 두 실행은 `.env`의 값을 셸 환경변수로 전달했다. 이 결과는 실행 전략의 차이를 보여주지만, 과제당 3회 반복만으로 PromptGuard가 gold보다 작업 수행에 유리하다고 일반화할 수는 없다.

실행별 데이터에서 비밀값 필요 과제의 promptguard 21회는 모두 정답 비밀의 원문 노출이 0이었다. 따라서 이 그룹의 높은 성공률을 탐지 누락으로 원문이 보였기 때문이라고 설명할 근거는 없다.

반면 비밀값 불필요 그룹에는 동일성 비교(`identity`)와 과잉 마스킹(`overmask`)에 취약한 과제가 포함된다. promptguard 전체 실패 8회 중 7회가 t14, t15, t23에서 발생해 이 그룹의 성공률을 낮췄다. 두 그룹의 성공률 차이는 비밀값 필요 여부만이 아니라 과제 구성과 실패 유형을 함께 반영한다.

## 7. 해석의 범위

- 현재 결과는 모델 하나, 과제 26개, 조건별 과제당 3회 반복이다. 개별 과제의 성공률 차이는 실행 변동의 영향을 받을 수 있다.
- 과제는 실패 유형을 드러내도록 직접 구성했다. 성공률의 절대값을 일반적인 코딩 작업 전체로 확대 해석하지 않는다.
- 비밀 노출률은 transcript의 사용자 쪽 행에서 정답 비밀의 정확한 문자열이 발견된 실행 비율이다. 이 수치가 0%라고 부분 문자열 등 모든 형태의 정보 노출이 없다는 뜻은 아니다.
- gold 역시 정답 비밀의 문자열 일치와 등록된 변형을 가리는 조건이다. 비밀의 일부만 출력된 경우까지 모두 차단하는 조건은 아니다.
- placeholder 원복 등 시스템 기능을 바꾸면 새로운 평가 조건이 된다. 기존 결과에 효과를 소급해서 적용하지 않고 같은 조건으로 다시 비교한다.
